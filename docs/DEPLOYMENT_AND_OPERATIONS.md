# راهنمای استقرار، بهره‌برداری و عملیات (Runbook) سامانه «اورژانس خودرو»

## ۱. پیش‌نیازهای استقرار عملیاتی (Production)
برای مسیر اجرایی، مدارک لازم و دروازه‌های تصمیم پایلوت قزوین، [برنامه آمادگی پایلوت](QAZVIN_PILOT_READINESS.md) را ببینید. این Runbook جایگزین اخذ مجوز یا تأیید ناوگان واقعی نیست.

- **نسخه Node.js:** نسخه `22.5.0` یا بالاتر (به دلیل استفاده از ماژول تراکنشی بومی `node:sqlite` بدون وابستگی به کامپایل C++ خارجی).
- **فایل پیکربندی محیطی:** کپی `.env.example` به `.env` و تنظیم مقادیر واقعی (هیچ کلید خصوصی نباید در Git ثبت شود):
  - `APP_ENV=production` و `NODE_ENV=production`؛ مقدار `NODE_ENV=production` حتی اگر `APP_ENV` اشتباه `development` باشد، seed را غیرفعال و قواعد Production را اعمال می‌کند.
  - `SESSION_SECRET`: رشته تصادفی حداقل ۳۲ کاراکتری (تولید با `openssl rand -hex 32`)
  - `FEATURE_ENABLE_DEV_SEED=false` (در Production سرور آن را مستقل از مقدار ورودی نیز خاموش می‌کند)
  - `FEATURE_ALLOW_EV_SERVICES=false` (پیش‌فرض امن) تا زمان تأیید تخصص و پوشش واقعی EV؛ ارائه خدمت EV به فعال بودن هم‌زمان پرچم محیطی و تنظیم `allow_ev_services=true` در دیتابیس نیاز دارد.
  - `FEATURE_ALLOW_POSTPAY_DEBT=false` به‌صورت پیش‌فرض؛ فعال‌سازی بعدی نیازمند بررسی حقوقی/عملیاتی و تأیید هر دو پرچم محیطی و دیتابیسی (`allow_postpay_debt=true`) است. ثبت بدهی، پرداخت بانکی نیست.
  - `PAYMENT_PROVIDER=zarinpal`، `ENABLE_SANDBOX_GATEWAY=false`، شناسه واقعی `ZARINPAL_MERCHANT_ID` و `ZARINPAL_SANDBOX=false`؛ هر نوع درگاه آزمایشی در Production باعث توقف راه‌اندازی می‌شود.
  - `SMS_PROVIDER=kavenegar`، `KAVENEGAR_API_KEY=<کلید وب‌سرویس واقعی>` و `SMS_SENDER_NUMBER=<خط خدماتی واقعی>`؛ صندوق آزمایشی پیامک در Production ممنوع است.
  - `ENABLE_PUBLIC_OPERATIONS=false` تا زمان اخذ مجوزهای لازم، تأیید نرخ‌نامه، تأمین ناوگان و خط تماس معتبر؛ فقط پس از تست پذیرش و تأیید صریح مالک محصول آن را `true` کنید. تا آن زمان API ثبت درخواست با `503 PUBLIC_OPERATIONS_DISABLED` پاسخ می‌دهد.
  - `DATABASE_PATH=/var/lib/auto-emergency/emscar.sqlite` (مسیر دیسک پایدار SSD با مجوز محدود `0600`)
  - `PRIVATE_STORAGE_DIR=/var/lib/auto-emergency/private_uploads`
  - `DATABASE_BACKUP_DIR=/var/backups/auto-emergency`

## ۲. دستورات مدیریت پایگاه‌داده، پشتیبان‌گیری و بازگردانی (Migration & Backup)

```bash
# ۱. بررسی وضعیت Migrationهای اعمال‌شده و در انتظار
npm run db:status

# ۲. تهیه نسخه پشتیبان اتمیک آنلاین پیش از هر تغییر اسکیما (مبتنی بر VACUUM INTO)
npm run db:backup

# ۳. اعمال Migrationهای جدید با کنترل هش یکپارچگی SHA-256
npm run db:migrate

# ۴. بازگردانی آخرین Migration در صورت بروز خطا (Rollback ایمن با اسکریپت .down.sql)
npm run db:rollback
```

> **قانون عملیاتی:** هرگز بدون اجرای `npm run db:backup` و تأیید صحت فایل تولیدشده در پوشه `backups/`، تغییر اسکیمای جدید یا عملیات اصلاحی روی دیتابیس Production اجرا نشود.

## ۴. پایش سلامت (Monitoring) و واکنش به رخدادها (Incident Response)

### ۴.۱ نقطه پایش سلامت (`GET /api/health`)
خروجی JSON اتصال دیتابیس، محیط اجرا و providerهای انتخاب‌شده/حالت Sandbox را برمی‌گرداند. وضعیت provider در این endpoint اتصال زنده را آزمایش یا اثبات نمی‌کند؛ پایش باید تراکنش/پذیرش مجاز واقعی را جداگانه و با رویهٔ ارائه‌دهنده راستی‌آزمایی کند. سامانه مانیتورینگ (مانند Prometheus Blackbox یا Uptime Kuma) می‌تواند هر ۳۰ ثانیه کد `200` و `"ok": true` این مسیر را پایش کند، اما این پاسخ به‌تنهایی آمادگی عملیاتی نیست.

### ۴.۲ سناریوی اختلال در سرویس پیامک خارجی
- خطای پنل پیامکی به هیچ عنوان تراکنش ثبت درخواست یا پرداخت را متوقف نمی‌کند.
- پیامک ناموفق با وضعیت `failed` ذخیره می‌شود و مدیر ارشد از تب **«تنظیمات، پیامک و لاگ ممیزی»** می‌تواند تلاش مجدد کند.
- وضعیت `sent` در جدول قدیمی اعلان‌ها فقط به معنی پذیرش درخواست توسط API کاوه‌نگار با شناسه واقعی پیام است؛ تحویل به گوشی در این نسخه تأیید نمی‌شود. `sandbox_logged` صرفاً ثبت محلی است، شناسه provider ندارد و پیامک واقعی نیست.

### ۴.۳ ثبت بدهی پس‌پرداخت (قابلیت خاموش پیش‌فرض؛ نه پرداخت)
- مسیر `POST /api/payments/staff/approve-debt` فقط وقتی قابل استفاده است که هر دو شرط محیطی `FEATURE_ALLOW_POSTPAY_DEBT=true` و دیتابیسی `allow_postpay_debt=true` برقرار باشند؛ هر دو به‌صورت پیش‌فرض خاموش‌اند.
- سرور فقط برای مأموریت `Completed` با فاکتور `issued` و بدون پرداخت درحال‌پردازش/وضعیت پرداخت نهایی اجازه ثبت می‌دهد. عملیات اتمیک و ممیزی می‌شود؛ پاسخ `paymentReceived: false` است و هیچ وجهی دریافت، تراکنش بانکی تأیید یا خودرو به‌طور خودکار ترخیص نمی‌شود.
- این قابلیت فقط پس از تصویب رویه مکتوب، بررسی حقوقی/مالی و آموزش کارکنان قابل بررسی است. برای پیگیری پرداخت واقعی باید از مسیر درگاه و تأیید سمت سرور استفاده شود.

### ۴.۴ درگاه، بازپرداخت و تسویهٔ بانکی
- `GET /api/payments/gateway-info` فقط provider انتخاب‌شده و حالت Sandbox را اعلام می‌کند؛ `connectionVerified=false` باقی می‌ماند تا هیچ ادعای اتصال از روی پیکربندی ساخته نشود. تنها نتیجهٔ معتبر استعلام سمت سرور برای همان تراکنش می‌تواند پرداخت را تأیید کند.
- صفحهٔ مالی، پرداخت‌های غیر-Sandbox تأییدشده را در جمع اصلی می‌آورد؛ Sandbox و رکوردهای قدیمیِ بدون مدرک به تفکیک و خارج از جمع اصلی گزارش می‌شوند.
- بازپرداخت در نسخهٔ فعلی مسدود است (`503 REFUND_PROVIDER_UNAVAILABLE`). این مسیر هیچ ردیف Refund، وضعیت پرداخت، فاکتور، دفترکل یا پیام موفقیت نمی‌سازد. تا پیاده‌سازی و آزمون provider واقعی، بازپرداخت باید طبق رویهٔ مالی خارج از سامانه پیگیری شود؛ ثبت آن در نرم‌افزار انجام نمی‌شود.
- درخواست تسویه به‌تنهایی واریز نیست. در Sandbox، تأیید مدیر فقط شبیه‌سازی است و هیچ پولی جابه‌جا نمی‌شود. در مسیر دستی غیر-Sandbox، مدیر باید ابتدا انتقال را خارج از سامانه انجام دهد و سپس مرجع واقعی، یادداشت ممیزی و checkbox تأیید مشاهدهٔ رسید را ثبت کند. برنامه انتقال یا استعلام خودکار بانکی ندارد؛ وضعیت این ردیف «ثبت دستی» است، نه تأیید provider.
- Migration 005 رکوردهای قدیمی Refund/Settlement را به `legacy_unverified` علامت می‌زند؛ آن‌ها در جمع‌های تأییدشده شمرده نمی‌شوند و در گزارش، جداگانه قابل مشاهده‌اند.

### ۴.۵ دستورالعمل فعال‌سازی استان جدید پس از قزوین
1. ورود با حساب **مدیر ارشد (`admin`)** به پنل `/admin` -> تب **«استان‌ها و زون‌های پوشش»**.
2. تعریف زون‌های شهری و جاده‌ای استان هدف (مثلاً البرز یا زنجان) و تخصیص خدمات مجاز.
3. ثبت‌نام، احراز مدارک و فعال‌سازی حداقل تعداد الزامی امدادگران بومی آن استان در تب **«تأیید و فعال‌سازی امدادگران»**.
4. بررسی شاخص آمادگی استان؛ تغییر وضعیت استان به `active` همراه با ثبت دلیل رسمی مصوبه که در `geography_status_history` و `audit_logs` ماندگار می‌شود.

## ۵. محدودیت‌های شناخته‌شده نسخه فعلی و نقشه راه مقیاس‌پذیری ملی
1. **پایگاه‌داده در مقیاس کشوری:** موتور فعلی `node:sqlite` در حالت `WAL` برای راه‌اندازی استان قزوین و چندین استان هم‌جوار روی سرور اختصاصی واحد (Single-Node) عملکرد بسیار سریع و تراکنشی دارد؛ اما برای استقرار چندسروره (Multi-Node Horizontal Scaling) در مقیاس ۳۱ استان کشور، مهاجرت لایه مخزن داده به **PostgreSQL + PostGIS** گام پیشنهادی فاز توسعه ملی است.
2. **کانال رویدادهای بلادرنگ (SSE):** مسیر احراز هویت‌شده `GET /api/events/stream` با فیلتر سطح دسترسی نقش‌محور (`RealtimeBus`) تغییرات مأموریت، پیشنهادهای اعزام و موقعیت زنده GPS امدادگر را بلادرنگ به کلاینت‌های مجاز ارسال می‌کند و Polling دوره‌ای نیز به‌عنوان پشتیبان پایداری شبکه حفظ شده است. در استقرار چندسروره آینده، جایگزینی حافظه داخلی با Redis Pub/Sub پیشنهاد می‌شود.
3. **خط لوله یکپارچه‌سازی مداوم (CI):** گردش‌کار `.github/workflows/ci.yml` روی هر Push و Pull Request بررسی امنیتی وابستگی‌ها، تایپ‌چک کامل، برگشت‌پذیری Migrationها، مجموعه تست‌های خودکار و بیلد Production را اجرا می‌کند.
4. **یکپارچه‌سازی سرویس‌های بیرونی:** تنظیمات پیش‌فرض توسعه (`PAYMENT_PROVIDER=sandbox` و `SMS_PROVIDER=sandbox_outbox`) صرفاً برای آزمون‌اند و نه پرداخت بانکی یا پیامک تحویل‌شده واقعی؛ نتیجه آن‌ها نباید موفقیت واقعی نمایش داده شود. پیکربندی Production هر نوع Sandbox را رد می‌کند و به مقادیر تجاری زرین‌پال و کاوه‌نگار نیاز دارد، اما وجود کلیدها به‌تنهایی اتصال پذیرفته‌شده، تسویه یا تحویل موفق را اثبات نمی‌کند؛ آزمون مجاز و تأیید سمت ارائه‌دهنده لازم است. نقشه پیش‌فرض `vector_qazvin` نیز پوشش شماتیک محلی است، نه مسیریابی/ترافیک زنده یا ETA تضمین‌شده. پیش از هر ادعای عملیاتی، وضعیت واقعی هر سرویس را مستقل بررسی کنید.
